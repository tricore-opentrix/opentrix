## 1. Proposed Q06 decision: S rather than N

- **Why S:** same scoped key + semantic payload can safely be replayed if *all* originals, concurrent resends, delayed originals, recovery jobs and cleanup/admission paths serialize through an approved Core transaction/unique-key fence. There must be no side effect outside the atomic Core commit.
- **Why not N as current direction:** a negative status lookup, absent receipt, expired row or released lock does **not** prove a delayed original cannot later commit. A valid N alternative would require a durable authoritative closure/admission barrier, not yet designed or verified.
- **Consumer protocol:** Helpdesk must durably persist original tenant/verified service principal/operation scope, resource identity, key, exact canonical semantic payload, expectedPolicyGeneration, incoming fencingSequence and separate business/assignment/Workflow version tokens **before first dispatch**. On lost ACK/timeout/unknown commit: authenticated status lookup **first**, verify original scope + current entitlement, match original fingerprint/attempt and then conditional CAS of current intent. A historical receipt is not current ACL authorization.
- **Conditional resend:** only the **same key + identical semantics/G/fence/versions**, after lookup, within *approved* admission/retention, with independently proved Core same-key serialization; no refreshed key/G/fence or reinterpretation of old canonical bytes. A missing/in-flight status is NOT non-commit proof.
- **Fail-closed default:** until shared contract and actual mechanism are reviewed/proven, **resend DISABLED**. Missing/unauthorized/ambiguous/expired/unavailable status or unmatched receipt keeps Helpdesk in RECONCILIATION_REQUIRED; escalate under separately approved operations policy. Never timeout-convert to SYNCHRONIZATION_FAILED, release Q08 reservation, or auto-switch to unsafe N.

### 2.3 Atomic invariant and PostgreSQL proof boundary

For each admitted ACL assignment identity, a committed successful replacement implies one immutable complete terminal receipt in the **same transaction** as exactly the approved ACL/G/fence/audit delta. Conversely rollback leaves none of those staged effects. Rejected terminal no-op, if Q02 selected, binds the key/outcome but has zero policy/fence/G/success-audit delta. Complete means approved non-null scope/key/fingerprint/canonical version/resource/operation/outcome and applicable business token/G/fence/audit references, not invented JSON fields. Receipt content must match actual effects; presence alone is insufficient.

Final-only order: **Tenant Guard → Scoped Key Serialization → current Authorization → fresh G/Fence Validation → ACL Mutation + Audit → Complete Terminal Receipt → COMMIT**. Pure ingress credential/shape/canonical validation occurs before DB; current lookup authorization under guard precedes receipt/conflict disclosure. Existing historical receipt is handled before fresh execution G/fence checks. No receipt means no row to row-lock: SELECT FOR UPDATE of a missing ledger row is not key serialization. For this tenant-bound scope the mandatory exclusive tenant guard may supply pre-mutation serialization; prove every path uses it, do not add an unnecessary advisory/key table by assumption. Unique scope constraint remains required.

Final-only does not durably bind an attempted key/fingerprint before commit. After a full rollback there is no stored fingerprint to prove a later different-payload request conflicts; H must preserve the original immutable intent and same-semantic resend. Do not promise server-side conflict against an erased attempt, or introduce detached reservation just to imply that guarantee. Same-key/different-payload conflict assertions below apply when identity was committed/retired; a stronger pre-commit attempt-binding promise needs a separate owner decision.

READ COMMITTED waits then uses a new statement snapshot for receipt/facts; original-first and retry-first serialize on same tenant guard, while higher fence/G from other commands may reject a fresh retry. A late final INSERT conflict after staged mutation is a protocol violation/error: **abort the whole operation**, including all policy/audit effects. Never ON CONFLICT DO NOTHING then COMMIT the staged mutation; rollback to clean transaction before any authorized receipt recovery. A savepoint must not preserve mutation while swallowing missing/failed receipt. If commit response is lost, retain uncertainty; neither empty status nor later rollback proves non-commit. [PostgreSQL isolation](https://www.postgresql.org/docs/17/transaction-iso.html), [explicit locks/savepoints](https://www.postgresql.org/docs/17/explicit-locking.html).

Early-reservation comparison only: [constraint triggers](https://www.postgresql.org/docs/17/sql-createtrigger.html) can be AFTER ROW DEFERRABLE; validate final stored row, not the transient INSERT image. WHEN is evaluated immediately, not at commit. SET CONSTRAINTS IMMEDIATE/savepoint/disable/DELETE and writers skipping the ledger still need proof. No early-reservation mechanism is approved by these PostgreSQL capabilities.

**Q07 security:** actual effective roles/grants are NOT VERIFIED from source templates. Capture memberships including SET ROLE, default/PUBLIC grants, ownership, overloads, schema CREATE, trigger-disable/replication settings and credential/pool access. Do not grant reader UPDATE(acl_revision) for row-lock acquisition: [SELECT privilege requirements](https://www.postgresql.org/docs/17/sql-select.html). Narrow lock-only definer versus transaction advisory locks remains Q07 PENDING; helper publication must CREATE/revoke PUBLIC/exact grant in one transaction with trusted fixed search_path and no dynamic SQL. [Definer guidance](https://www.postgresql.org/docs/17/sql-createfunction.html#SQL-CREATEFUNCTION-SECURITY). Separate lock helper from a potential restricted mutation executor; one does not establish the other's receipt invariant.

### 2.4 Minimal retention/restore admission proposal — Q05 not selected

Retain dedup identity without expiry in MVP. Initially retain full terminal receipts and rejection outcomes; no automatic cleanup schedule or duration invented. If outcome payload compaction is later separately approved, replace under the same guard/key transaction with a durable tombstone preserving scope/key/fingerprint/canonical version/exact resource-incarnation and approved terminal/admission information. Preserve enough rejection outcome for the promised X-24 replay, or approve explicit expired-history semantics without allowing new execution. Tombstone is neither a progress row nor permission to execute again; no MVP identity deletion/reuse. Unbounded storage/PII is residual cost requiring owner policy, not silently solved by TTL.

Cleanup-first, resend-first and delayed original all use guard→key; no identity absence window. A never-admitted key with no durable retirement may still become the first execution if current auth/G/fence/admission permits: lateness alone is not an expiry rule. Claiming cancellation/non-admission of such a delayed original requires an approved durable scoped retirement/closure under the same guard, not a local H timeout; that mechanism/authority is OPEN. Core admission is closed before restore/import/issuer remapping; reopening requires reconciliation of all acknowledged/possibly committed command identities/tombstones, G, fence, resource incarnations and canonical service mapping with durable recovery evidence. Backup before a commit may omit its receipt: simply restoring ACL/G/fence from that backup does not reconstruct dedup identity. If any acknowledged/uncertain commit gap cannot be recovered or late originals cannot be safely excluded, keep admission/resend closed and escalate; never infer fresh intent from absence. Exact operating authority/reopening evidence remains Q05/Q09 BLOCKED, not a new API or epoch field. Out-of-scope Create must get its own equivalent proof; assignment fence alone cannot dedup Create.

### Core atomic execution/replay oracle (proposed)

1. Verify exact authenticated caller, tenant/resource scope and current authority for the requested *lookup*; no status/receipt disclosure before it. Fail closed on tenant mismatch, hidden resource or revoked service scope.
2. In a fresh command transaction, acquire tenant exclusive guard **before any key/ACL mutation**, then serialize/read the exact scoped identity under the all-writer guard protocol; no early ledger INSERT in the preferred Final-only candidate. Database unique identity is the backstop, not a final-stage substitute for pre-mutation serialization. Empty lookup is not non-commit evidence.
3. If a matching terminal receipt exists, return historical result under current lookup permission, without re-evaluating old execution G/fence preconditions or writing ACL/G/fence/audit again. If fingerprint differs, conflict/no mutation.
4. If no committed receipt wins and identity is *currently admissible*, independently re-authorize the requested execution, check fresh expected G and incoming resource fence, then atomic replace managed grant slice + fence + G + audit + **complete keyed terminal result as last write before COMMIT**. Failed/skipped/incomplete receipt must not allow effects to commit; required DB/writer boundary is unresolved. SQL/transaction failure before commit rolls back all; commit uncertainty stays unknown.
5. Serialize **every** original/resend/delayed arrival through the same protocol, including independently authorized maintenance/cleanup writers. Retired keys cannot become fresh after archive/restore. No network call inside Core transaction; Helpdesk only finalizes separate local current-intent CAS.
